# Contributing - Conventions

Rules followed by the code, the tests and the documentation of the repository.

## Repository layout

```text
.
├── bach.sh                  # The `bach` function: loads (and downloads) the libraries and calls their functions
├── tests.sh                 # Test runner
├── Makefile                 # Development commands (see Usage)
├── libs/
│   ├── <lib>.sh             # A library
│   ├── <lib>.test.sh        # Its tests
│   └── <lib>.md             # Its documentation (published on the site)
├── demo/<lib>/              # Runnable demonstration of a library (demo.sh, README.md)
├── docs/                    # Documentation site: VitePress config, theme, scripts, contributing pages
├── .skill/                  # Coding and documentation standards of the repository
├── README.md                # Presentation, install and usage of bach (home of the site)
└── TODO.md                  # Work in progress ideas
```

A library `libs/<lib>.sh` is called with `bach <lib>` (function `bach::<lib>`) or `bach <lib>::<function>` (function `bach::<lib>::<function>`). The name of the file is the name of the library.

## Bash

### File structure

- Start with the shebang `#!/bin/bash`.
- Then a comment block with the description, usage, dependencies, author and version.
- Then the re-sourcing guard, then the functions, each one followed by `export -f` when it is public.

```bash
#!/bin/bash

################################################################################
# My Library
################################################################################
# Description:
#   What the library does.
#
# Usage:
#   source /path/to/my_lib.sh
#   bach my_lib::my_function "arg"
#
# Dependencies:
#   - bash 4.0+
#
# Author: BACHCLI Project
# Version: 1.0.0
################################################################################

# Prevent re-sourcing if functions already declared
if declare -F bach::my_lib::my_function &>/dev/null; then
    return 0
fi
```

### Functions

- **Names**: `bach::<lib>::<name>` for public functions, `bach::<lib>::__private::<name>` for private ones. A library with one main function names it `bach::<lib>`.
- **Docstring**: a comment block immediately above each function: description, `Arguments`, `Globals`, `Outputs`, `Returns`.
- **Size**: one responsibility, about 30 lines of logic at most.
- **Variables**: arguments are read into `local` variables with default values at the beginning of the function; no global variable except the documented ones (prefixed `__BACH_`).
- **Results**: output on stdout, status code `0` on success and non zero on failure. Avoid subshells and command substitutions; pass the name of a variable (nameref) to return values when needed.
- **Messages**: user messages use `printf` (or `bach log`) and go to stderr, so that stdout stays usable. Debug messages stay in the code, commented and clearly marked as such.

```bash
################################################################################
# Get the extension of a file name
# Arguments:
#   $1 - file_name: Name of the file
# Outputs:
#   The extension on stdout
# Returns:
#   0 on success, 1 if the file name has no extension
################################################################################
bach::my_lib::get_extension() {
    local file_name="${1:-""}"
    [[ "$file_name" == *.* ]] || return 1
    printf '%s\n' "${file_name##*.}"
}
export -f bach::my_lib::get_extension
```

## Tests

- Each library has a test file in the same folder: `libs/<lib>.test.sh`.
- Tests use the `assert` library (`bach::assert::section`, `bach::assert::contains`, `bach::assert::empty`...) and end with `bach::assert::print_test_summary`, whose status code is the exit code of the file.
- Test functions are named `test_<what_is_tested>` and called from a `main` function; they are grouped by feature with `bach::assert::section`.
- Cover every public function: nominal cases, edge cases and error handling. Update the tests with every change.

## Documentation

### Libraries

Each library has a documentation page `libs/<lib>.md`, added to the sidebar in `docs/.vitepress/config.mts`. It is example-based and contains, in this order:

1. `# <lib>.sh - <Title>`: title and one sentence description.
2. `## Overview` and `## Features`.
3. `## Usage Examples`: one `###` heading per example, with a short introduction and a `::: code-group` containing a `With bach` and a `Standalone` snippet. Each example covers one feature, including edge cases and errors. The "Expected output" blocks are generated by `make doc:fix`, never written by hand.
4. Reference sections specific to the library.
5. `## API Reference`: one `###` heading per public function with description, signature, parameters, output and returns.
6. `## Roadmap` and `## See Also`.

The documentation must be updated with every change of the code: new feature, new option, changed behavior.

### Other pages

- `README.md`: introduction, install, usage and versions of bach.
- `docs/contributing/`: these contributing pages.
- Write in English, with clear and concise language, and test every example.

## Commit messages

Commit messages follow [Conventional Commits](https://www.conventionalcommits.org): `<type>(<scope>): <summary>`, with a type among `feat`, `fix`, `docs`, `test`, `refactor` and `chore`, and the library as scope (`feat(parse_args): ...`). The body explains what changed and why.
